# Optional GitHub setup checker

The [reusable checker](../.github/workflows/check-github-setup.yml) is a read-only diagnostic for the [one-time setup guide](setup-guide.md), independent of release authorization. It runs on GitHub-hosted Windows, uses GET-only bounded settings requests, prints no tokens or raw API bodies and makes no host calls. It never gates deployment or writes GitHub settings.

Use the [manual diagnostic example](examples/check-github-setup.yml); replace its immutable checker SHA with a reviewed revision. Manual dispatch here runs only the optional diagnostic, not a release. Inputs are `application_id` (required), `channel` (DEV by default, or Production), `integration_branch` (master by default), optional `runner_group` for organization access inspection, and `check_release_immutability` (true by default). Environment and runner labels derive from application ID and channel. No routing variable or workflow allowlist input is required.

The seven default categories inspect branch protection, version-tag protection, native Restrict actors, tag workflow trigger, environment, repository-accessible runners and release immutability. Their links point to the corresponding sections of the ten-section guide. An explicitly requested organization group adds an access observation. Repository-scoped runners work without that category. Selected group workflow allowlists are not a CLC prerequisite. The environment must allow tags without branch restrictions, reviewers, wait timers or additional deployment approval rules. Confirm Active Restrict actors coverage of all workflows and no event restrictions manually.

Each category reports CONFIGURED, NEEDS CONFIGURATION or CHECK MANUALLY. Confirmed discrepancies take precedence over incomplete evidence. Native repository-wide Restrict actors policy and workflow-code review remain CHECK MANUALLY with direct GitHub links: the checker does not invent API evidence or parse a workflow trust graph. Inherited/hidden bypass, denied APIs, malformed responses and incomplete pagination also remain manual. Optional inspection credentials must be read-only and narrowly scoped; the default GITHUB_TOKEN may lack settings visibility.

Tag protection distinguishes usable creation from immutability. A visible active creation restriction without tag-capable bypass reports NEEDS CONFIGURATION, including a proven overlapping blocker that another ruleset cannot override. Creator bypass of a combined creation/update/deletion ruleset requires independent immutability protection. Even when separate no-bypass update/deletion restrictions are visible, the checker reports CHECK MANUALLY for designated creators and effective permissions across all applicable rulesets. Complex or partially excluded scopes remain manual where coverage cannot be established. See [the concrete configuration](setup-guide.md#3-protect-release-tags).

The separate Release immutability category inspects repository settings; it does not certify a particular published Release. Application publication independently requires actual API Boolean `immutable=true` on the canonical Release. Both tag protection and Release immutability are required.

Outputs remain exactly `status`, `configured_count`, `needs_configuration_count` and `manual_count`. The summary supplies literal settings navigation and links for unresolved observations. No result grants host enrollment, standing authority, release execution or operational readiness. Prepare/enroll hosts and complete separately authorized [deployment/recovery verification](iis-verification.md).

Run the mocked API tests, syntax, workflow YAML/actionlint and documentation-link checks with `tools/github-setup-check/tests/Test.ps1 -PesterManifestPath <verified-Pester.psd1> -ActionlintPath <verified-actionlint.exe>`. Dependencies remain pinned in the existing lock files. Offline tests do not establish actual IIS or independent-identity qualification.
