# Optional GitHub setup checker

The reusable checker is a read-only diagnostic for one-time setup. It runs on GitHub-hosted Windows and uses bounded, GET-only settings requests. Its diagnostic output shows configuration findings and omits sensitive request and response data. Routine releases rely on the repository's GitHub controls. [Reusable checker](../.github/workflows/check-github-setup.yml) · [Setup guide](setup-guide.md)

Use the [manual diagnostic example](examples/check-github-setup.yml); replace its immutable checker SHA with a reviewed revision. Manual dispatch here runs only the optional diagnostic, not a release. Inputs are `application_id` (required), `channel` (DEV by default, or Production), `integration_branch` (master by default), optional `runner_group` for organization access inspection, and `check_release_immutability` (true by default). Environment and runner labels derive from application ID and channel. No routing variable or workflow allowlist input is required.

The seven default categories inspect branch protection, version-tag protection, native Restrict actors, tag workflow trigger, environment, repository-accessible runners and release immutability. Their links point to the corresponding GitHub setup sections. An explicitly requested organization group adds an access observation. Repository-scoped runners work without that category. Selected group workflow allowlists are not a CLC prerequisite. For unattended application deployments, the checker expects the GitHub environment's deployment branches and tags setting to be **No restriction**, with required reviewers, wait timers and other deployment protection rules disabled. Confirm Active Restrict actors coverage of all workflows and no event restrictions manually.

Each category reports CONFIGURED, NEEDS CONFIGURATION or CHECK MANUALLY. Confirmed discrepancies take precedence over incomplete evidence. Native repository-wide Restrict actors policy and workflow-code review remain CHECK MANUALLY with direct GitHub links: the checker does not invent API evidence or parse a workflow trust graph. Inherited/hidden bypass, denied APIs, malformed responses and incomplete pagination also remain manual. Optional inspection credentials must be read-only and narrowly scoped; the default GITHUB_TOKEN may lack settings visibility.

Tag protection distinguishes usable creation from immutability. A visible active creation restriction without tag-capable bypass reports NEEDS CONFIGURATION, including a proven overlapping blocker that another ruleset cannot override. Creator bypass of a combined creation/update/deletion ruleset requires independent immutability protection. Even when separate no-bypass update/deletion restrictions are visible, the checker reports CHECK MANUALLY for designated creators and effective permissions across all applicable rulesets. Complex or partially excluded scopes remain manual where coverage cannot be established. [Release tag setup](github-setup.md#2-protect-release-tags)

The separate Release immutability category inspects repository settings; it does not certify a particular published Release. Application publication independently requires actual API Boolean `immutable=true` on the canonical Release. Both tag protection and Release immutability are required.

The outputs are `status`, `configured_count`, `needs_configuration_count` and `manual_count`. The summary supplies settings navigation and links for unresolved observations. The server and application owners coordinate permission and scope for live deployment and recovery verification. [IIS acceptance](iis-verification.md)

Run the mocked API tests, syntax, workflow YAML/actionlint and documentation-link checks with `tools/github-setup-check/tests/Test.ps1 -PesterManifestPath <verified-Pester.psd1> -ActionlintPath <verified-actionlint.exe>`. Dependencies remain pinned in the existing lock files. Offline tests do not establish actual IIS or independent-identity qualification.
