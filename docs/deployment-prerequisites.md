# Read-only deployment prerequisite checker (report contract 3)

For a new target, follow the [Deployment Setup Guide](setup-guide.md) first. It provides the configuration sequence independently of this diagnostic; use report links to resolve remaining findings. Intentional manual-only workflows need the [workflow compatibility review](setup-guide.md#review-intentional-workflow-differences), not automatic trigger changes to satisfy static inspection.

Use this checker during initial commissioning, when onboarding or migrating a target, after meaningful infrastructure changes, or when troubleshooting. Missing infrastructure is expected diagnostic input: the hosted GitHub stage can run before a runner group, environment, release workflows or enrolled host exist. It answers whether the required infrastructure is configured sufficiently to attempt a separately authorized initial deployment. Routine deployments do not require a checker report.

1. Select the exact repository, integration branch, application/environment/target/channel and required workflow paths to inspect. Independently configure missing infrastructure using the findings; actual-host inspection requires its separately authorized trusted toolkit and host path.
2. Run the manually invoked [consumer diagnostic workflow](examples/deployment-readiness.yml), with exact reviewed source pins and explicit application/environment/target/channel selectors.
3. Correct blocking findings using the indicated resource and setting. The checker performs no corrections.
4. Rerun if necessary.
5. Proceed with the separately authorized initial deployment. An empty, correctly enrolled target can be READY without a deployed application, current-release approval, historical journals/backups or standing authorization.
6. Complete application-specific deployment and recovery acceptance under its own scope. Actual Windows Server 2022/IIS and independent-identity qualification remain **NOT RUN**.

The checker never approves deployment, installs or upgrades the toolkit, enrolls a target, changes GitHub/IIS/ACLs, creates approvals, clears state, or executes application validators, hooks, planning code, readiness requests or migrations. Deployment retains its independent approval, locking, preflight and recovery checks. The merged architecture is [master c552e724bd0508798312f579f208dc438ed39c51](https://github.com/clcdpc/clc-deployment/tree/c552e724bd0508798312f579f208dc438ed39c51); its [contracts](https://github.com/clcdpc/clc-deployment/blob/c552e724bd0508798312f579f208dc438ed39c51/docs/contracts.md) distinguish protected source/caller/shared-job identities from installed toolkit identity.

## Run and interpret

The [template](examples/deployment-readiness.yml) defines a manual consumer workflow with three jobs: hosted GitHub inspection, directly defined and independently admitted actual-host inspection, then hosted aggregation with `if: always()`. It is a template, not an installed workflow or authority. Replace all diagnostic zero SHA pins with one reviewed immutable diagnostic revision; separately pin the shared orchestration SHA matching protected `.clc/release.json`. Independently allowlist the exact job-defining shared deployment workflow and the consumer diagnostic workflow. Keep privileged runners and infrastructure credentials outside ordinary PR CI.

Hosted inspection is also available independently:

```powershell
# GH_TOKEN supplies ordinary read access. Administrative settings may need the
# explicit protected read-only installation token described below.
& ./tools/Validate-DeploymentPrerequisites.ps1 `
    -ApplicationId example-app -TargetId example-app-dev -EnvironmentName example-app-dev `
    -IntegrationBranch master -ReleaseWorkflow .github/workflows/build.yml `
    -DeploymentWorkflow .github/workflows/deploy.yml -DeploymentChannel DEV `
    -RunnerGroup example-app-dev -RunnerLabels self-hosted,Windows,X64 `
    -SharedRevision $reviewedOrchestrationSha -DiagnosticWorkflow .github/workflows/diagnose-deployment.yml `
    -YamlAssemblyPath $verifiedYamlAssembly -ReportPath $localReport
```

On the independently admitted enrolled host, use trusted diagnostic source and the exact independently approved installed manifest:

```powershell
$hostReport = & ./tools/deployment-prerequisites/Test-DeploymentHost.ps1 `
    -ApplicationId example-app -TargetId example-app-dev -EnvironmentName example-app-dev `
    -Repository example-org/example-app -IntegrationBranch master -DeploymentChannel DEV `
    -ReleaseWorkflow .github/workflows/build.yml -BuildJob build `
    -ToolkitManifestPath $independentlyApprovedInstalledManifest
# Optional -StandingAuthorizationId selects an existing policy for advisory inspection.
# It is not required for commissioning and never authorizes initial deployment.
```

Both inspectors emit structured findings for normal prerequisite failures. Successful diagnostic execution can exit zero with NOT READY findings. Invalid inputs, unauthenticated executable dependencies or inability to produce a valid report are command errors. The final `Merge-DeploymentReadiness.ps1` publishes available findings, exits zero only for READY and nonzero for NOT READY or report-generation failure. There is no Strict switch or configurable failure policy.

During commissioning, callers may pass `runner_group: ${{ vars.EXPECTED_RUNNER_GROUP }}` even while that variable is missing, pass `runner_group: ''`, or omit the optional reusable input (default empty). The PowerShell entry point likewise accepts `-RunnerGroup ''` or omission. `github.runner.group` then reports a required FAIL with the action to configure and independently provision the expected dedicated group. No default group is invented, selected from a list or inferred, and no runner-group API lookup runs without an explicit name. Do not create a placeholder group merely to run the diagnostic.

Missing, null or explicitly empty expected runner labels produce a separate required `github.runner.labels` FAIL, including when the group name is also missing. Malformed or unsupported expected labels also FAIL with corrective syntax guidance; labels are never trimmed or normalized. Omission of the optional script/workflow labels input retains `self-hosted,Windows,X64`; an explicit empty value does not use that default. The existing bounds remain 1–10 comma-separated labels, each 1–64 ASCII letters/digits/underscores/dots/hyphens starting with a letter or digit.

An exact resource absent from a complete accessible list is FAIL. Inaccessible administrative settings, concealed 404 responses, incomplete collections and unavailable group-detail identities remain UNVERIFIED. Missing required workflow files at an identity-verified readable source are FAIL; inaccessible workflow APIs remain UNVERIFIED. Dependent checks use SKIPPED with the unavailable prerequisite as their reason. Independent repository, branch/tag protection, workflow and environment observations continue when safely possible, and completed observations survive an unexpected checker failure. Missing runner expectations cannot make workflow-access, additional privileged-job or target-routing comparisons PASS; independently confirmed security failures remain FAIL. A missing caller cannot establish direct/shared applicability. A verified direct caller does not require shared orchestration configuration; actual shared calls retain the reviewed immutable revision requirement.

With a verified repository identity, missing or unreadable integration-branch evidence skips source-dependent workflow/routing inspections while tag protection, runner configuration/visibility/advisories and environment inspections continue. Missing expected runner configuration cannot hide confirmed shared-channel scope collisions or literal contradictions in every direct deployment route. Dynamic or reusable direct selectors remain inconclusive where static evidence cannot establish their routing. An omitted environment-policy field is UNVERIFIED; an explicitly null unrestricted policy is FAIL. Unexpected inspection errors remain required UNVERIFIED findings, retain completed findings and cannot produce READY.

Malformed repository/branch/application/target/workflow selectors, unsupported channels/authentication modes, unsafe nonempty group names, malformed immutable revisions or installed manifest selectors, and untrusted YAML/executable dependencies retain fail-closed invocation or authentication failures. A syntactically valid expected resource name never proves existence or grants execution authority. The diagnostic does not provision or repair any missing resource, and missing configuration cannot yield READY.

READY means both GitHub and actual-host categories PASS: all required applicable prerequisites have sufficient practical evidence. It may contain visible advisory warnings. NOT READY means a required prerequisite failed, remained inconclusive or was skipped. A GitHub-only or host-only report cannot establish overall READY.

The Markdown job summary starts with compact readiness, subject, category statuses and separate underlying check counts. Its **Outstanding prerequisites** table has three columns: Status, Prerequisite and Explanation. Status includes Required or Advisory. Every FAIL comes before UNVERIFIED, then SKIPPED; within each status, Required precedes Advisory, then GitHub precedes host, with ordinal identity as the final tie-breaker. Advisory failures remain visible without blocking readiness. Missing or incomplete inspections remain explicit.

Explicit source-owned setup groups combine related branch/tag/environment/IIS/state findings only when status, impact and category agree. A group sorts by its smallest member ID and lists each finding in ordinal check-ID order, with an individual actionable link to the specific [setup instructions](setup-guide.md). Single findings use ordinary explanations. Runner repository/workflow admission and registration remain distinct tasks. Grouped rows never reduce the header counts or mutate JSON. Every known FAIL links to a fixed master setup-guide anchor, including safe investigation/recovery destinations for integrity or state failures. Intentional manual-only workflow differences link to compatibility review rather than prescribing trigger changes.

Concise labels and status-aware operator guidance come from source-owned check-ID mappings; skipped checks reference known prerequisite reasons. Unknown checks or actions use conservative technical-detail guidance. **Passed and not applicable checks** are collapsed with their combined count and distinct statuses/impacts. Collapsed **Technical details** retain every original check ID, category, status, impact, name, detail, action and dependency reason in ordinal ID order, plus integration branch and observed commit. Dynamic text is escaped as text and embedded line breaks/control characters normalized, so observations cannot create Markdown rows or HTML structure. These presentation changes leave JSON contract 3, source diagnostic fields, check ordering, Actions outputs, readiness and merger exit semantics unchanged.

If complete escaped evidence exceeds GitHub's [1 MiB step-summary limit](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#step-isolation-and-limits), the summary retains the full checklist and a technical check-ID/category/status/impact index, with an explicit notice directing operators to the existing JSON report for all original evidence. JSON is never truncated and no extra artifact is created.

| Check status | Meaning |
| --- | --- |
| PASS | Executed and obtained sufficient evidence |
| FAIL | Confirmed missing, incorrect, disabled or incompatible prerequisite |
| UNVERIFIED | Attempted but inconclusive: denied access, incomplete API/native evidence, unsupported configuration or concurrent change |
| SKIPPED | Did not execute; reason identifies the missing dependency or inspection stage |
| NOT_APPLICABLE | A source-defined applicability condition was established, such as a verified empty target with no current release |

Each check has an explicit source-owned Required or Advisory classification. Required FAIL blocks; required UNVERIFIED/SKIPPED prevents PASS. Legitimate NOT_APPLICABLE does not block. Advisory findings retain their actual status and corrective action without independently blocking readiness. Categories use FAIL precedence, otherwise UNVERIFIED for incomplete required inspection, otherwise PASS. Human titles have no role in aggregation.

## What is inspected

| Area | Required observations and practical limits |
| --- | --- |
| Repository/source | Exact consumer identity and configured integration branch (`master` or `main`), required CI checks, force-push/deletion and observable bypass restrictions. Mandatory PR reviews, reviewer counts, CODEOWNERS and extra PR-branch protection are not universal requirements. |
| Release tags | Active applicable creation/update/deletion rules and observable bypass restrictions for the selected channel. Names/patterns alone and evaluate-only rules are insufficient. Simple full or channel-specific coverage is supported; complex exclusions remain inconclusive. DEV and Production are the only deployment channels; DEV snapshots rely on the protected integration source and explicit source policy. |
| Workflows/routing | Expected producer/caller source at one observed integration commit, bounded valid YAML, trigger handoff, exact immutable shared deployment/publication references, the existing strict shared consumer configuration contract (including trusted files and required toolkit contract), protected application/channel/target/environment/group/labels and actual shared job routing. Disabled activation indicators are pending activation warnings, never host authority. Legacy direct routing can be inspected, but absent protected channel configuration remains inconclusive. |
| Environment | Exact environment and exact configured integration-branch-only policy with no unexpected branch/tag admission. Reviewers are optional compatibility information, not a new pipeline approval requirement. |
| Runner admission | Exact selected repository access with correct public/private admission; selected-workflow enforcement and no additional workflows; actual job-defining shared workflow rather than consumer caller; an online group runner with expected labels. Wrong or overbroad allowlists FAIL; inaccessible required settings remain UNVERIFIED. Cross-organization shared use requires observed inherited enterprise ownership. Correct observable restrictions can PASS with an advisory enterprise-enforcement limitation. |
| Toolkit trust | Trusted diagnostic bootstrap authenticates the fixed protected installation policy before candidate import, checks active version/source/distribution/inventory and required dependencies, and holds authenticated files/physical identities across import and inspection. Candidate code cannot authenticate itself. The initial authority anchor accepts SYSTEM/Administrators writers; other infrastructure writer patterns remain inconclusive without importing candidate code. |
| Host/IIS/filesystem | Actual machine and admitted elevated deployment identity; exact protected enrollment; dedicated IIS site/root application/pool/path/runtime SID/one-worker settings; Server 2022/x64 PowerShell/.NET/ANCM; external configuration/key directories and existing physical-path/ACL/Authz observations. Runtime remains distinct and nonadministrator with effective protected-resource write isolation. No probe writes or application execution. |
| Canonical state | Existing lock opened read-only/exclusive without creation or modification, pending admission, journal/current/terminal/helper reconciliation, and engine initial-empty-state rules. Populated targets retain current approved manifest/inventory and generated schema-2/3 standing-revocation checks. No historical ZIP or unrelated recovery-backup campaign is required. Unresolved/corrupt/unsafe evidence blocks readiness; diagnostics never reconcile it. |
| Optional automation | Missing standing policy or baseline does not block initial commissioning. A selected existing policy is checked for scope/protection; warnings do not certify routine unattended release eligibility. |

Branch inspection combines classic protection with GitHub's [active effective rules for the configured branch](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch), including inherited rulesets. Ruleset-only protection can pass without a classic protection record. An inaccessible classic endpoint, including a potentially concealed 404, is not evidence of absence: independently observed rulesets must establish any required controls that classic data cannot establish. For each required control, classic `enforce_admins` or an independently enforcing ruleset must restrict broad bypass. [Layered rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#about-rule-layering) can supply that independent enforcement. Ruleset inspection checks actor IDs and bypass modes, rejects broad repository/enterprise-role or administrator/owner bypass when no independent control enforces the restriction, and leaves malformed actor lists, unknown actor representations, contradictory evidence or inaccessible required details inconclusive. Specifically selected teams, apps and users remain subject to independent infrastructure ownership; their identities alone do not establish future behavior. GitHub's [DeployKey API contract](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset) uses an explicit `actor_id=null`, which does not identify one approved key. Its `always` or `exempt` bypass is potentially broad and blocks protection unless another applicable restriction independently enforces the required branch control. Numeric, missing or malformed DeployKey IDs and `pull_request` mode remain UNVERIFIED.

GitHub's [Get a repository ruleset endpoint](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset) withholds `bypass_actors` unless the requester has write access to the ruleset. An otherwise valid active response with this property omitted preserves independently observed restrictions. The required branch/tag bypass checks assess observable protection and confirmed bypass defeats; their PASS does not verify hidden actors. The advisory `github.branch.bypass-visibility` and `github.tags.bypass-visibility` checks report UNVERIFIED with an explicit visibility warning when GitHub omits relevant actors, PASS when relevant actor information is fully observable, and SKIPPED only when the corresponding inspection did not run. Unavailable or malformed actor evidence also remains visible as UNVERIFIED and blocks required checks wherever needed to establish protection. Read-only omission alone does not prevent READY or require write-capable credentials. A hidden list cannot cancel a confirmed broad bypass; only independently established enforcement can do so.

Selected tag coverage follows the [standard release contract](shared-release-orchestration.md): `vMAJOR.MINOR.PATCH-dev.N` routes to DEV and stable versions to Production. Beta/RC tags remain artifact-only; their protection is not required for automatic deployment eligibility. `-test.N` is unsupported and there is no separate Test release channel. Infrastructure environment names do not imply channels. Supported full-coverage patterns include `~ALL`, `refs/tags/*`, `refs/tags/v*`, `refs/tags/v*.*.*`, and the DEV suffix on `v*` or `v*.*.*` for DEV. Creation, update and deletion restrictions may come from multiple applicable active rulesets. A finite set of literal-prefix, exact-tag and known channel-pattern cases establishes disjointness before exclusions or other unavailable detail can affect the result. Historical `refs/tags/v*-test.*` and `refs/tags/v*.*.*-test.*` patterns are demonstrably disjoint from both supported deployment channels and are ignored before exclusions or unavailable bypass information; they cannot satisfy DEV or Production protection. This applicability classification does not accept Test releases. Applicable exclusions and ambiguous overlaps remain UNVERIFIED; this checker does not interpret arbitrary GitHub glob patterns. Relevant inaccessible ruleset details remain blocking, and parent rulesets remain included.

Static inspection cannot prove every future workflow expression, administrator/bypass action or enterprise enforcement behavior. Those limitations remain visible advisories when observable critical configuration is sufficient. Missing security-critical settings or unavailable required observations remain blocking. Application startup, database access, HTTPS readiness, operational configuration semantics, Data Protection compatibility and deployment/recovery acceptance require separately authorized application evidence. There is no certificate, expiration timer, report database, signoff or ongoing health monitor.

## Authentication, limits and reports

GitHub observation uses fixed-origin GET-only APIs, no redirects, bounded pagination (20 pages/2,000 items), 150 requests/240 seconds, 20-second requests and 4 MiB API responses. Workflow/config files are bounded to 256 KiB, with bounded safe JSON/YAML parsing. YAML aliases are rejected for consumer observations; the independently pinned shared definition permits bounded data-only alias interpretation. The YAML assembly and test tools retain [reviewed dependency pins](../tools/deployment-prerequisites/dependencies.lock.json).

Standard hosted inspection uses the caller's GitHub token. Administrative mode is explicit: a short-lived read-only GitHub App installation token in `inspection_token`, available only to the hosted `deployment-configuration-inspection` environment on protected-branch manual dispatch. Required organization runner/protection APIs may be unavailable to ordinary `GITHUB_TOKEN`; that produces UNVERIFIED, never a bypass. No administrative token enters the actual-host job. Shared diagnostic checkout requires GitHub.com's independently observed job workflow repository/path/SHA and fails before checkout if unavailable; it never falls back to caller source. Hosted smoke scenarios exercise this platform dependency through the actual reusable entry point with both an explicit group name and empty group/labels, checking contract-3 findings and all count outputs without starting actual-host inspection.

Report version **3** intentionally rejects version 2. The report contains `contract_version`, `subject` (repository, integration_branch, application, target, environment, channel, observed_commit), `checked_at_utc`, `github_status`, `host_status`, Boolean `ready`, status `counts` and `checks`. Every check contains stable `id`, explicit `category`, human `name`, `status`, Boolean `required`, safe `detail`, corrective `action` and stable `reason` (empty when unused). JSON values have consistent types.

Aggregation rejects unsupported/malformed/oversized reports, unknown or duplicate check IDs, wrong category/classification, missing fields, contradictory summaries/counts and mixed subjects. Omitted known required checks cannot grant PASS. It preserves valid findings and corrective actions, including confirmed failures from unsuccessful stages. A missing stage adds one SKIPPED inspection finding, not invented host observations. Ordering is deterministic by ID. Reports are bounded to 1 MiB, 500 checks and 4,096 characters per text field. Only sanitized authored diagnostics are published; no private exception text, API response, token, operational configuration or credentials are emitted.

Reusable outputs are `report_json`, `github_status`, `host_status`, `ready`, and `passed_count`, `failed_count`, `unverified_count`, `skipped_count`, `not_applicable_count`. The JSON contract uses nested `counts`; Actions count/readiness outputs are strings. Final reporting uses `always()` to publish available results after failed or skipped inspection jobs. These outputs are troubleshooting observations and have no deployment-admission role.
