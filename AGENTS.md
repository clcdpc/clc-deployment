# Repository guidance

This repository contains the CLC.Deployment toolkit, Clc.Deployment.AspNetCore companion and infrastructure-owned host enrollment tooling, with shared tag-driven releases. Actual Windows Server 2022/IIS and independent-identity qualification remain NOT RUN. Real host provisioning/execution and all consumer/DEV work require explicit scope authorization. Before development or operational work, read README.md, docs/contracts.md, docs/deployment.md, docs/installation.md, docs/host-enrollment.md and docs/iis-verification.md.

- Keep V1 to Windows Server 2022, PowerShell 7, file-only ASP.NET Core/IIS, one dedicated site/application/pool and one worker. Use one protected installed toolkit, conventional private functions, explicit parameters and four public commands. No bundled engine, dynamic plugins, callbacks or orchestration framework.
- Use strict error handling, literal paths, parameter validation and bounded operations. Keep native IIS/process operations behind narrow internal functions that tests can mock.
- Authenticate release execution through infrastructure-owned, protected exact-byte approvals. Self-declared hashes, manifests, inspection results, caller expectations and release IDs never authorize execution. Toolkit installation and approval policy are independently trusted and pinned; no latest-branch execution.
- Optional standing authorization admits signed receipts from an exact pinned reusable GitHub producer into protected schema-2 exact approvals. Keep tag eligibility central, DEV/production separate and revocation effective on direct approval retries. It cannot authorize enrollment, initial baseline/cutover, toolkit changes, downgrades or exceptional recovery; generated-release recovery requires an independent schema-1 exact approval.
- Validate archives, hashes, physical path identities, aliases, hard links, reparse points, protected directories, runtime environment, identities and access observations before destructive mutation. Fail closed. Unexpected files are not cleanup candidates.
- Keep build/configuration semantics/readiness/database compatibility application-owned. Keep accounts, credentials, IIS/TLS/ACL provisioning, protected approvals, toolkit installation and permanent configuration infrastructure-owned.
- Initial V1 uses one shared deployment account with local administrator membership only on managed IIS servers; deployment/recovery require its enabled elevated administrator token. Independent infrastructure approval remains procedural against that administrator, outside ordinary NTFS containment. Preserve infrastructure ownership, structural ACLs and byte/path integrity; never grant its individual SID protected-resource write ACEs. Runtime remains distinct and nonadministrator, including group-derived authority, with effective protected-resource write isolation.
- Never put credentials or operational configuration in source, artifacts or logs. Never provision accounts or install secrets during deployment. Approved application validation executes with elevated deployment privileges; do not claim sandboxing or least privilege. Trusted deployment workflows may invoke independently authorized infrastructure enrollment and separately approved releases; keep privileged hosts/credentials outside ordinary PR CI and contributor-controlled code. Defer delegated IIS/JEA/broker/nonprivileged validation hardening until actual IIS reliability qualification.
- Idempotency requires verified bytes, effective configuration, host state and expected-release readiness. Serialize the actual machine/pool with one exclusive OS file handle owned by the mutation process. Persist intent before effects and reject unresolved attempts after a crash.
- Before replacement, an ordinary failure may restore the prior pool state only with proven unchanged approved files, compatible configuration and exited helpers. After replacement begins, use bounded stop/observation and retain recovery material; no automatic file restore or prior-version restart. An initially stopped pool must return stopped on failure when stopping can be proven. Explicit recovery checks approval, bytes, compatibility and helper-process quiescence before effects; uncertainty requires operator intervention.
- The simplified phase journal is version 2; legacy per-file/retirement journals are unsupported. Unexpected OS reboot during physical replacement may require manual recovery; no startup hook, activation broker or persistent activation fence is part of this model.
- Never claim success before readiness, final hashes and durable current/terminal state. Report actual pool/worker state, retained material and concrete operator actions. Never infer database rollback safety.
- Prefer deterministic offline PowerShell contracts and negative tests proving rejection before mutation. Require actual Windows/IIS qualification and consumer acceptance before claiming operational readiness; record skips and unrun gates honestly.
- Pin code and test dependencies to reviewed, verified versions. Version contracts explicitly and reject unsupported/legacy blueprint formats. Record the executing toolkit version/source/distribution identity in each attempt.
- Keep contracts, deployment/recovery guidance, verification procedures and tests consistent. Cite fixed source revisions when making existing-behavior claims.
- Do not change consumer repositories without explicit authorization. Favorite Authors, ASAP and Library Scheduler remain read-only; consumer changes require their own implementation task. Do not perform real IIS, identity-provider, directory-service, database or network operations in documentation or foundation tasks.
- For authorized development/documentation tasks, verify the remote integration branch (currently master), fetch, preserve user work, branch with codex/, review/test, commit/push and open a PR when requested. Do not merge without explicit authorization.

- Host enrollment stays outside the four-command module. Get/Plan are read-only; Apply needs a protected, exact machine/config/bootstrap/toolkit/operation approval. Use one fixed machine enrollment at `%ProgramData%\CLC\Deployment\Enrollment`, its existing host-policy/target artifacts and canonical machine/pool lock/state. Missing records with prior resources, lock, intent or state require reconciliation; never auto-repair or approve a release.
- Infrastructure scripts may provision only approved dedicated directories, ACLs and stopped IIS settings. Existing conventional service-account pools are reused; new pools require an already installed managed service account. Accounts, secrets, certificates, machine trust and component installation remain external. Legacy cutover requires exact independent authority, an already Stopped/zero-worker pool and a verified retained backup; no automatic stop/start/restore.
- Adoption proceeds through consumer-owned application compatibility, authorized enrollment automation, a separately authorized consumer deployment/recovery pilot, then separately scoped disruptive/destructive verification. A disposable probe application is not a prerequisite for consumer deployment/recovery evidence. Follow docs/iis-verification.md; actual real-host qualification remains NOT RUN.
